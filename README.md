Задание 1. СУБД
    1.1
        Кейс: Бюджетирование проектов с формированием финансовых отчётов и прогнозированием рисков. СУБД должна гарантировать целостность и чёткую структуру данных.
        Ответ: Реляционная СУБД (SQL) — PostgreSQL, Oracle, MS SQL Server. Причины: строгая структура данных, ACID-транзакции, возможность сложной аналитики.

    1.1*
        Кейс: Хеширование стало занимать длительное время. Какое API можно использовать для ускорения работы?
        Ответ: OpenSSL, Libsodium, pgcrypto в PostgreSQL; либо вынести хеширование в отдельный сервис или отдельные потоки (async).

    1.2
        Кейс: Под каждый девелоперский проект создаётся отдельный лендинг. Все данные по лидам стекаются в CRM к маркетологам и менеджерам по продажам. СУБД должны быть гибкими и быстрыми.
        Ответ: Для лендингов — NoSQL документная СУБД (MongoDB, Firebase). Для CRM — реляционная SQL-сУБД (PostgreSQL, MySQL). Причины: лендинги — гибкость схемы и высокая скорость записи, CRM — сложные связи и транзакции.

    1.2*
        Кейс: Можно ли закрыть задачу одной СУБД?
        Ответ: Да — PostgreSQL с JSONB. Позволяет комбинировать SQL-структуру и хранение документов в формате JSON, сохраняя производительность.

    1.3
        Кейс: Отдел контроля качества создаёт базу корпоративных норм и обучающих материалов. СУБД должна иметь простую и понятную структуру.
        Ответ: NoSQL документная БД (MongoDB) или PostgreSQL + JSONB. Удобно хранить документы различной структуры и классифицировать по категориям.

    1.3*
        Кейс: Можно ли использовать уже существующую СУБД из задач выше?
        Ответ: Да — PostgreSQL + JSONB. Создать отдельную таблицу для материалов и хранить документы в JSONB.

    1.4
        Кейс: Логистика нуждается в быстром формировании маршрутов доставки материалов по объектам и распределению курьеров. СУБД должна быстро работать со связями.
        Ответ: Графовая СУБД (Neo4j, JanusGraph). Причины: маршруты — это графы, эффективный поиск кратчайших путей.

    1.4*
        Кейс: Можно ли к этой СУБД подключить отдел закупок или лучше создать отдельную СУБД?
        Ответ: Можно подключить через API, если задачи имеют схожие связи. Но чаще: логистика — графовая БД, закупки — реляционная. Оптимально разделять.

    1.5*
        Кейс: Можно ли все перечисленные задачи решить одной СУБД?
        Ответ: Теоретически — PostgreSQL с JSONB и расширениями PostGIS/pgRouting. Практически — лучше комбинировать SQL + графовую БД.

Задание 2. Транзакции
    2.1
        Кейс: Пользователь пополняет баланс счёта телефона. Опишите шаги успешной транзакции.
        Ответ:
            1. Пользователь инициирует платёж.
            2. Создаётся запись о транзакции.
            3. Проверяется наличие средств на карте/счёте.
            4. Банк списывает деньги (ACID-транзакция).
            5. Оператор связи увеличивает баланс телефона.
            6. Транзакция фиксируется (COMMIT) и отправляется уведомление пользователю.

    2.1*
        Кейс: Если пополнение происходит через автоплатёж, какие действия должны выполняться?
        Ответ:
            1. Автоплатёж запускается по расписанию.
            2. Проверяется минимальный баланс телефона.
            3. Проверяется карта/способ оплаты.
            4. Выполняется списание и пополнение.
            5. Логируется автоплатёж.
            6. Отправляется уведомление пользователю.

Задание 3. SQL vs NoSQL
    3.1
        Кейс: Напишите пять преимуществ SQL-систем по отношению к NoSQL.
        Ответ:
            1. Строгая структура данных.
            2. ACID-транзакции.
            3. Возможность сложной аналитики.
            4. Универсальный язык SQL.
            5. Подходит для финансов, CRM и учёта.

    3.1*
        Кейс: Какие преимущества у NewSQL перед SQL и NoSQL?
        Ответ:
            1. Горизонтальное масштабирование (как NoSQL).
            2. ACID-транзакции (как SQL).
            3. Высокая производительность на больших нагрузках.
            4. Распределённая архитектура.
            5. Стандартный SQL-интерфейс.

Задание 4. Кластеры
    Кейс: Необходимо производить большое количество вычислений на 1000 машинах.
    Ответ:
        Критерии выбора СУБД: объём данных, масштабируемость, распределённая обработка.
        Оптимальные СУБД: ClickHouse, Cassandra, CockroachDB, TiDB.
        Модель распределённых вычислений: Spark (in-memory) или MapReduce. Причины: эффективная обработка больших данных и распределённые вычисления.
