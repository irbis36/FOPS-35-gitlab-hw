## Задание 1. СУБД

### 1.1. Бюджетирование проектов с аналитикой и прогнозированием рисков
Кейс: Крупная строительная компания, которая также занимается проектированием и девелопментом, хочет вести бюджетирование проектов, формировать финансовые отчёты и прогнозировать риски. Необходимо, чтобы СУБД гарантировала целостность и чёткую структуру данных.  
Ответ: Для таких задач лучше всего подойдёт **реляционная СУБД (PostgreSQL, MySQL, Oracle)**. Она обеспечивает строгую структуру данных, поддерживает транзакции ACID, что критично для финансовых расчётов, а также позволяет строить сложные аналитические запросы и отчёты.

### 1.1* Хеширование стало занимать длительное время
Кейс: Процесс хеширования данных оказался медленным, необходимо ускорить.  
Ответ: Можно использовать **Redis** как кэш или внешнее API для ускорения обработки. Это позволит хранить промежуточные результаты хеширования и значительно ускорить операции.

### 1.2. Лендинги и CRM
Кейс: Для каждого девелоперского проекта создаётся отдельный лендинг. Все данные по лидам стекутся в CRM к маркетологам и менеджерам по продажам. СУБД должны быть гибкими и быстрыми.  
Ответ: Для лендингов лучше использовать **NoSQL-систему (MongoDB, Firebase)** для гибкой схемы и быстрого чтения/записи данных. Для CRM можно использовать **NoSQL или гибридную СУБД** (например PostgreSQL с JSONB), чтобы легко хранить разные структуры данных по лидам.

### 1.2* Можно ли использовать одну СУБД?
Ответ: Да, можно использовать **PostgreSQL с поддержкой JSONB**, которая объединяет реляционную структуру и гибкость NoSQL, чтобы закрыть обе задачи (лендинги и CRM).

### 1.3. База данных для отдела контроля качества
Кейс: Необходимо создать базу по корпоративным нормам, правилам, обучающему материалу. СУБД должна иметь простую и понятную структуру.  
Ответ: Подойдет **реляционная СУБД (PostgreSQL, SQLite)**, потому что структура данных фиксированная, легко создавать таблицы, связи и отчёты, а интерфейс управления прост для обучения сотрудников.

### 1.3* Можно ли использовать СУБД из задач выше?
Ответ: Да, можно использовать PostgreSQL из задачи 1.1 или 1.2, создав отдельные схемы или таблицы для контроля качества, чтобы не смешивать финансовые данные и данные обучения.

### 1.4. Логистика
Кейс: Департамент логистики нуждается в быстром формировании маршрутов доставки материалов по объектам и распределении курьеров с доставкой документов. СУБД должна быстро работать со связями.  
Ответ: Для таких задач лучше всего подходит **графовая СУБД (Neo4j, JanusGraph)**. Она позволяет строить маршруты, рассчитывать кратчайшие пути, распределять курьеров и оптимизировать маршруты доставки.

### 1.4* Подключение отдела закупок
Ответ: Можно подключить отдел закупок к графовой СУБД через API, либо создать отдельную реляционную базу для закупок и связывать её с графовой СУБД логистики.

### 1.5* Можно ли использовать одну СУБД для всех задач?
Ответ: Теоретически можно использовать **PostgreSQL с расширениями JSONB и PostGIS**, чтобы закрыть все задачи (финансы, CRM, контроль качества, логистика), но для графовых задач и маршрутов будет менее удобно, чем использовать отдельную графовую СУБД.

## Задание 2. Транзакции

### 2.1. Пополнение баланса телефона
Кейс: Пользователь пополняет баланс счёта телефона.  
Ответ: Шаги транзакции:
1. Пользователь инициирует пополнение через приложение или сайт.  
2. Система проверяет доступные средства на источнике платежа.  
3. Система резервирует сумму на источнике платежа.  
4. Баланс пользователя обновляется в базе данных.  
5. Транзакция фиксируется (COMMIT).  
6. Пользователь получает подтверждение успешного пополнения.

### 2.1* Автоплатёж
Кейс: Пополнение происходит автоматически по расписанию.  
Ответ: Шаги:
1. Система инициирует транзакцию по расписанию автоплатежа.  
2. Проверка доступных средств на источнике.  
3. Резервирование суммы.  
4. Обновление баланса.  
5. Отправка уведомления пользователю о пополнении.  
6. Фиксация транзакции (COMMIT) и логирование.

## Задание 3. SQL vs NoSQL

### 3.1. Преимущества SQL перед NoSQL
1. Строгая структура данных.  
2. Поддержка ACID-транзакций.  
3. Мощный язык запросов SQL.  
4. Надёжность при изменении схемы.  
5. Хорошая совместимость с аналитическими инструментами и BI-системами.

### 3.1* Преимущества NewSQL
Ответ: NewSQL объединяет преимущества SQL (ACID, реляционные схемы) с масштабированием NoSQL (горизонтальное масштабирование, распределённые вычисления), позволяя обрабатывать большие объёмы данных без потери консистентности.

## Задание 4. Кластеры

Кейс: Необходимо выполнять большое количество вычислений при работе с огромным количеством данных на 1000 машинах.  
Ответ: Критерий выбора СУБД — **масштабируемость и поддержка распределённых вычислений**.  
Лучше всего подходит модель **MapReduce** или распределённая база данных типа **Hadoop/HBase, CockroachDB, Spark SQL**. Они позволяют параллельно обрабатывать данные на тысячах узлов и эффективно масштабировать нагрузку.
