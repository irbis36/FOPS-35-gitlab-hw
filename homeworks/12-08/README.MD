## Задание 1. Резервное копирование

### 1.1. Восстановление данных в полном объёме за предыдущий день

Здесь подойдёт **полное резервное копирование (full backup)** — раз в сутки делается полная копия всей базы данных. Это самый простой и понятный вариант: если что-то сломалось, берём вчерашний бэкап и восстанавливаем. Минус в том, что потеряем всё, что было записано за сегодня — но задача именно такая и есть, восстановить «вчера».

Для MySQL это можно сделать через `mysqldump`, для PostgreSQL через `pg_dump`. Запускается по расписанию через cron раз в 24 часа, например в 00:00.

---

### 1.2. Восстановление данных за час до поломки

Одним полным бэкапом тут не обойтись — если делать его раз в сутки, потеряем до 23 часов данных. Здесь нужна связка:

- **Полный бэкап** раз в сутки (как база)
- **Инкрементное копирование** или **бинарные логи (binlog / WAL)** — фиксируют каждое изменение в базе в режиме реального времени

При восстановлении сначала поднимается полный бэкап, а затем поверх него воспроизводятся логи вплоть до нужного момента времени. Таким образом можно восстановить состояние базы с точностью до минуты или даже до конкретной транзакции.

В PostgreSQL для этого используется механизм **PITR (Point-in-Time Recovery)** на основе WAL-архивов. В MySQL — инкрементные бэкапы через **mysqlbinlog** или инструмент **Percona XtraBackup**.

---

### 1.3.* Моментальное переключение на работающую базу

Да, такой сценарий возможен — это уже не про резервное копирование как таковое, а про **репликацию и высокую доступность (High Availability)**.

Схема работает так: рядом с основной базой (master) постоянно работает реплика (slave), которая получает все изменения в режиме реального времени. При поломке master-сервера балансировщик (например, HAProxy или Keepalived) автоматически переключает трафик на реплику — это занимает секунды.

Для MySQL такой режим реализуется через **MHA (Master High Availability)** или **Orchestrator**. В PostgreSQL — через **Patroni** в связке с etcd. Резервное копирование при этом тоже остаётся — репликация защищает от отказа железа, но не от случайного `DROP TABLE`.

## Задание 2. PostgreSQL

### 2.1. Резервное копирование и восстановление через pg_dump / pg_restore

**Создание резервной копии:**

```bash
# Дамп конкретной базы данных в бинарном формате (-Fc)
pg_dump -U postgres -h localhost -Fc -d my_database -f /backup/my_database.dump

# Дамп в читаемом SQL-формате
pg_dump -U postgres -h localhost -d my_database -f /backup/my_database.sql
```

**Восстановление из резервной копии:**

```bash
# Восстановление из бинарного дампа
pg_restore -U postgres -h localhost -d my_database /backup/my_database.dump

# Восстановление из SQL-файла
psql -U postgres -h localhost -d my_database -f /backup/my_database.sql
```

Флаг `-Fc` (custom format) удобен тем, что позволяет восстанавливать выборочно — отдельные таблицы или схемы, а не всю базу целиком. Ещё можно добавить `-j 4` к `pg_restore` для параллельного восстановления в 4 потока — на больших базах заметно ускоряет процесс.

---

### 2.1.* Автоматизация резервного копирования PostgreSQL

Да, автоматизировать можно и нужно. Самый простой способ — скрипт + cron.

**Скрипт `/usr/local/bin/pg_backup.sh`:**

```bash
#!/bin/bash

DATE=$(date '+%Y-%m-%d_%H-%M')
BACKUP_DIR="/backup/postgres"
DB_NAME="my_database"
PG_USER="postgres"

mkdir -p "$BACKUP_DIR"

pg_dump -U "$PG_USER" -Fc -d "$DB_NAME" -f "$BACKUP_DIR/${DB_NAME}_${DATE}.dump"

if [ $? -eq 0 ]; then
    logger -t pg_backup "SUCCESS: Бэкап $DB_NAME создан -> ${DB_NAME}_${DATE}.dump"
    # Удалить бэкапы старше 7 дней
    find "$BACKUP_DIR" -name "*.dump" -mtime +7 -delete
else
    logger -t pg_backup "ERROR: Ошибка при создании бэкапа $DB_NAME"
fi
```

**Cron — запуск каждый день в 02:00:**

```cron
0 2 * * * /usr/local/bin/pg_backup.sh
```

Для более серьёзных задач существуют готовые инструменты — **pgBackRest** и **Barman**. Они умеют инкрементные бэкапы, сжатие, шифрование, хранение в S3 и PITR из коробки. Но для начала вполне хватает скрипта с cron.

## Задание 3. MySQL

### 3.1. Инкрементное резервное копирование MySQL

Инкрементный бэкап сохраняет только те данные, которые изменились с момента последнего бэкапа. Для MySQL это реализуется через **Percona XtraBackup** — стандартный `mysqldump` инкрементные бэкапы не поддерживает.

**Полный бэкап (делается первым, как базовый):**

```bash
xtrabackup --backup \
  --user=root \
  --password=rootpass \
  --target-dir=/backup/full
```

**Инкрементный бэкап на основе полного:**

```bash
xtrabackup --backup \
  --user=root \
  --password=rootpass \
  --target-dir=/backup/inc_1 \
  --incremental-basedir=/backup/full
```

**Восстановление — сначала подготовка, потом применение:**

```bash
# Подготовить полный бэкап
xtrabackup --prepare --apply-log-only --target-dir=/backup/full

# Применить инкрементный поверх полного
xtrabackup --prepare --apply-log-only \
  --target-dir=/backup/full \
  --incremental-dir=/backup/inc_1

# Финальная подготовка
xtrabackup --prepare --target-dir=/backup/full

# Восстановить данные
xtrabackup --copy-back --target-dir=/backup/full
```

Второй способ — через **бинарные логи (binlog)**. Если binlog включён, можно восстановить базу до любой точки:

```bash
# Посмотреть список бинарных логов
mysqlbinlog /var/lib/mysql/mysql-bin.000001 | mysql -u root -p
```

### 3.1.* Когда реплика выгоднее обычного резервного копирования

Реплика и резервная копия решают разные задачи, но реплика даёт ряд преимуществ:

**1. Актуальность данных.** Бэкап — это снимок базы на момент создания. Реплика синхронизируется в реальном времени и отстаёт от master на секунды. При сбое потеря данных минимальна.

**2. Скорость восстановления.** Восстановление из бэкапа большой базы может занять часы. Переключение на реплику — секунды.

**3. Снижение нагрузки на master.** Бэкап через `mysqldump` или `xtrabackup` нагружает сервер. Если снимать бэкап с реплики, master не затрагивается вообще.

**4. Защита от аппаратного сбоя.** Если сервер с master физически вышел из строя, реплика на другом сервере уже готова к работе.

Однако реплика **не заменяет** бэкап полностью: если кто-то случайно выполнит `DROP TABLE` или `DELETE` без `WHERE`, это изменение мгновенно реплицируется на все реплики. Бэкап в этом случае — единственный способ вернуть данные. Поэтому правильный подход — использовать **и репликацию, и резервное копирование** одновременно.
