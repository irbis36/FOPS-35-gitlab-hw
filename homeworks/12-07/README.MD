## Задание 1. Преимущества методов масштабирования

### Активный Master + пассивный Slave (резервный)

В данной схеме slave-сервер не обслуживает пользовательские запросы, а находится в режиме ожидания и непрерывно получает изменения от master через репликацию.

**Преимущества:**

- **Отказоустойчивость** — при падении master slave немедленно переводится в активный режим (failover), время простоя минимально
- **Актуальная резервная копия** — slave всегда содержит свежие данные, в отличие от периодических бэкапов
- **Безопасное обслуживание** — обновления, патчи и технические работы можно проводить на master без потери доступности: slave берёт нагрузку на себя
- **Простота архитектуры** — один поток репликации, нет конфликтов, предсказуемое поведение

---

### Master + несколько Slave-серверов (масштабирование чтения)

В данной схеме все slave-серверы активно обслуживают запросы на чтение, а master принимает только запросы на запись.

**Преимущества:**

- **Горизонтальное масштабирование чтения** — нагрузку SELECT можно распределить между произвольным количеством slave-серверов; добавление нового slave не требует остановки системы
- **Разделение нагрузки** — аналитические и тяжёлые отчётные запросы уходят на отдельные slave, не влияя на производительность master
- **Географическое распределение** — slave-серверы размещаются ближе к пользователям в разных регионах, снижая задержки
- **Изоляция задач** — отдельные slave можно выделить под конкретные задачи: один для аналитики, другой для бэкапов, третий для пользовательского трафика

## Задание 2. План горизонтального и вертикального шардинга

### Описание базы данных

Исходная база содержит три таблицы:

**users** — пользователи:
`user_id`, `name`, `email`, `region`, `registered_at`

**books** — книги:
`book_id`, `title`, `author`, `genre`, `price`, `publisher`

**shops** — магазины:
`shop_id`, `name`, `city`, `region`, `address`, `phone`

---

### Вертикальный шардинг

При вертикальном шардинге таблицы разнесли по отдельным базам данных по смысловому признаку — каждая база отвечает за свою предметную область.

| База данных | Таблицы | Сервер | Режим |
|---|---|---|---|
| `db_users` | users | Server A | Master + Slave |
| `db_catalog` | books | Server B | Master + Slave |
| `db_geo` | shops | Server C | Master + Slave |

Каждый сервер работает в паре Master–Slave: master принимает запись, slave обслуживает чтение и выступает резервом при отказе.

**Принцип:** разные сущности имеют разные паттерны нагрузки. Каталог книг читают намного чаще чем пишут — его slave масштабируется независимо. Пользовательская база требует строгой консистентности — она изолирована от остальных.

---

### Горизонтальный шардинг

При горизонтальном шардинге таблицу `users` разбили по строкам — по признаку региона пользователя. Каждый шард содержит только часть данных.

| Шард | Условие | Сервер | Режим |
|---|---|---|---|
| `db_users_shard1` | region = 'RU' | Server A1 | Master + Slave |
| `db_users_shard2` | region = 'EU' | Server A2 | Master + Slave |
| `db_users_shard3` | region = 'US' | Server A3 | Master + Slave |

Маршрутизация запросов осуществляется через прокси-слой (например, ProxySQL или приложение), который определяет нужный шард по полю `region`.

**Принцип:** ни один шард не содержит полную таблицу пользователей, поэтому нагрузка и объём данных распределены равномерно. Добавление нового региона = добавление нового шарда без изменения существующих.

---

---

### Режимы работы серверов

| Сервер | Роль | Режим |
|---|---|---|
| Server A1/A2/A3 (users shards) | Шарды пользователей | Каждый: Master на запись + Slave на чтение |
| Server B (catalog) | Каталог книг | Master на запись + 2×Slave на чтение (высокая нагрузка чтения) |
| Server C (geo) | Магазины | Master на запись + Slave резерв |
| ProxySQL | Маршрутизатор | Активный, без хранения данных |

### Итоговые принципы

- **Вертикальный шардинг** разделение таблицы по смыслу — независимое масштабирование каждой предметной области
- **Горизонтальный шардинг** разделение таблицы users по регионам — линейный рост ёмкости при добавлении шардов
- Каждый шард работает в связке **Master + Slave**: master принимает запись, slave обслуживает чтение и является горячим резервом
- Единая точка входа через **ProxySQL** скрывает от приложения всю сложность маршрутизации
