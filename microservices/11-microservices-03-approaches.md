# Домашнее задание к занятию «Микросервисы: подходы»

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.


## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

---

```

↓
GitLab CI/CD
↓
Docker Registry
↓
Kubernetes / Servers
```

## Обоснование

### 1. Полный DevOps lifecycle
- Git + CI/CD + Registry в одном продукте
- Уменьшение количества интеграций

### 2. Гибкость пайплайнов
- `.gitlab-ci.yml` (Infrastructure as Code)
- Поддержка:
  - шаблонов (`include`)
  - параметров (`variables`)
  - разных окружений

### 3. Запуск сборок
- по push / merge request
- вручную (manual jobs)
- по расписанию

### 4. Секреты
- GitLab CI Variables (masked, protected)
- интеграция с Vault

### 5. Масштабируемость
- self-hosted runners:
  - Docker
  - Kubernetes
- параллельные job’ы

### 6. Кастомизация
- собственные Docker-образы
- любые шаги сборки (bash, scripts)

- централизует DevOps процессы
- масштабируется
- уменьшает сложность поддержки

## Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.

```

## Обоснование

### 1. Минимальные требования к приложениям
- сбор из stdout (12-factor app)

### 2. Надежность
- буферизация во Fluentd
- retry-механизмы
- кластер Elasticsearch

### 3. Поиск и аналитика
- мощный full-text search
- фильтрация и агрегации

### 4. UI
- Kibana:
  - сохраненные запросы
  - shareable ссылки
  - dashboards

### 5. Kubernetes-ready
- Fluentd как DaemonSet
- автосбор логов контейнеров

# Почему EFK, а не ELK

## Ключевое различие

| Компонент | ELK | EFK |
|----------|-----|-----|
| Агент сбора логов | Logstash | Fluentd |
| Основная роль | Тяжёлый ETL-процессор | Легковесный лог-агрегатор |
| Использование | Централизованный ingestion | Edge-сбор (на каждом хосте) |

---

## 1. Архитектурная разница

### ELK
```Service → Logstash → Elasticsearch → Kibana```


### EFK

```Service → Fluentd → Elasticsearch → Kibana``
---

## 2. Почему Logstash хуже в роли агента

### Недостатки Logstash:
- Высокое потребление ресурсов (JVM)
- Долгий старт
- Плохо масштабируется как DaemonSet
- Сложнее в эксплуатации

 Logstash — это скорее **центральный процессор логов**, а не агент

---

## 3. Преимущества Fluentd

### Легковесность
- написан на C/Ruby
- значительно меньше потребляет CPU/RAM

### Kubernetes-first
- стандартный DaemonSet
- автоматически собирает stdout контейнеров

### Надежность
- буферизация на диск
- retry механизмы
- защита от потери логов

### Гибкость
- плагины:
  - парсинг
  - маршрутизация
  - фильтрация

---

## 4. Масштабирование

| Критерий | Logstash | Fluentd |
|----------|----------|---------|
| Горизонтальное масштабирование | Сложное | Простое |
| Работа на каждом узле | Плохо подходит | Идеально |
| Kubernetes | Неудобен | Стандарт |

---

## 5. Практика индустрии

- ELK — классика для **VM/legacy систем**
- EFK — стандарт для:
  - Kubernetes
  - микросервисов
  - cloud-native систем

---


## Итог

EFK — это:
- стандарт индустрии
- масштабируемость
- мощный анализ логов

## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.
---

## Рассматриваемые решения

| **Prometheus + Grafana** | Да | Да | Да | Grafana | De-facto стандарт |
| **Zabbix** | Да | Да | Ограничено | Встроенный | Тяжеловесный |

## Выбор: **Prometheus + Grafana**

---

## Архитектура
```
Exporters (node_exporter, app metrics)
↓
Prometheus
↓
Grafana
```

---

## Обоснование

### 1. Сбор метрик
- node_exporter → CPU, RAM, disk, network
- cAdvisor → контейнеры
- кастомные метрики → /metrics endpoint

### 2. Модель данных
- time-series база
- язык запросов PromQL

### 3. Масштабируемость
- federation
- remote storage

### 4. UI
- Grafana:
  - гибкие dashboards
  - алерты
  - агрегации

### 5. Стандарт индустрии
- нативная интеграция с Kubernetes
- поддержка большинства сервисов

---

## Итог

**Prometheus + Grafana**:
- гибкость
- мощный анализ
- масштабируемость
