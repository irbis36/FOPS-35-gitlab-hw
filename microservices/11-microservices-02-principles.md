## Задача 1: API Gateway 

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:
- маршрутизация запросов к нужному сервису на основе конфигурации,
- возможность проверки аутентификационной информации в запросах,
- обеспечение терминации HTTPS.

Обоснуйте свой выбор.
# Ответ

Для крупной компании выбор API Gateway должен опираться на:
- возможность управления "как кодом" (Infrastructure as Code)
- наличие плагинной системы (чтобы не писать кастомный код)
- способность выдерживать высокие нагрузки

## Сравнительная таблица API Gateway

| Решение | Конфигурация | Аутентификация | HTTPS | Расширяемость | Эксплуатация | Комментарий |
|--------|-------------|----------------|-------|---------------|--------------|-------------|
| **Kong** | Декларативная (YAML/DB) | Плагины | Да | Высокая | Средняя | Хороший баланс, но зависимость от плагинов |
| **Traefik** | Динамическая (Docker/K8s) | Middleware | Да | Средняя | Простая | Отличен для Dev/Test, слабее в enterprise security |
| **Nginx** | Статическая (конфиги) | Через auth_request / Lua | Да | Ограниченная | Средняя | Надежен, но требует кастомной логики |
| **Envoy Proxy** | xDS API (динамика) | Фильтры (JWT, ext_authz) | Да | Очень высокая | Сложная | De-facto стандарт в service mesh |
| **HAProxy** | Конфиги | ACL + Lua | Да | Средняя | Средняя | Быстрый, но менее гибкий |

---

## Выбор: **Envoy Proxy + внешний auth сервис**

### Почему не Kong
- Плагинная модель ограничивает гибкость
- Stateful-конфигурация (DB mode) усложняет GitOps
- Vendor lock-in при использовании Enterprise

---

## Обоснование выбора Envoy

### 1. Архитектурная гибкость
- Использует **xDS API** → полностью динамическая конфигурация
- Отлично интегрируется с Kubernetes (Istio, Consul)

### 2. Аутентификация
- JWT проверяется встроенным фильтром
- Поддержка **external authorization (ext_authz)**:
  - можно вынести auth в отдельный сервис (security)

### 3. Производительность
- L7 proxy на C++
- Высокая пропускная способность и низкие latency

### 4. HTTPS
- TLS termination встроен
- Поддержка mTLS

### 5. Observability
- Метрики (Prometheus)
- Трейсинг (Jaeger)
- Логи

---

## Итог

**Envoy — это не “просто gateway”, а универсальный data-plane**, который:
- масштабируется горизонтально
- не требует переписывания логики при росте системы
- соответствует production-grade требованиям

## Задача 2: Брокер сообщений 

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:
- поддержка кластеризации для обеспечения надёжности,
- хранение сообщений на диске в процессе доставки,
- высокая скорость работы,
- поддержка различных форматов сообщений,
- разделение прав доступа к различным потокам сообщений,
- простота эксплуатации.

Обоснуйте свой выбор.

# Ответ
В микросервисной архитектуре брокер сообщений — это сердце системы. Требования комбинируют надежность (кластер, диски) со скоростью и гибкостью.

## Сравнительная таблица

| Решение | Кластер | Диск | Скорость | Форматы | ACL | Эксплуатация | Комментарий |
|--------|--------|------|----------|---------|-----|--------------|-------------|
| **Apache Kafka** | Отличная (KRaft) | Да | Очень высокая | Ограничено | Сложная | Сложная | Стандарт для стриминга |

---

## Выбор: **RabbitMQ**

---

## Обоснование

### 1. Надежность
- Quorum Queues (Raft)
- Гарантированная запись на диск

### 2. Гибкость
- Не ограничивает формат сообщений
- Поддержка сложной маршрутизации (exchange, routing key)

### 3. Безопасность
- ACL:
  - Users
  - Virtual Hosts
  - Permissions

### 4. Эксплуатация
- Встроенный UI
- Простая диагностика
- Легче Kafka в поддержке

### 5. Баланс
Kafka выигрывает в throughput, но:
- сложнее в эксплуатации
- требует отдельной команды

RabbitMQ — оптимальный комприсс.

--- который экономит время DevOps на дебаге. 


# Задача 3*: API Gateway (реализация)

## Выбор: **Nginx как API Gateway**

Почему:
- проще всего реализовать в рамках docker-compose
- поддерживает auth_request
- легко воспроизводится локально

---
## Конфигурация Nginx:

```nginx
events {}

http {
    upstream security {
        server security:8080;
    }

    upstream uploader {
        server uploader:8080;
    }

    upstream minio {
        server minio:9000;
    }

    server {
        listen 80;

        location = /v1/register {
            proxy_pass http://security/v1/user;
        }

        location = /v1/token {
            proxy_pass http://security/v1/token;
        }

        location = /auth {
            internal;
            proxy_pass http://security/v1/token/validation;
            proxy_pass_request_body off;
            proxy_set_header Content-Length "";
            proxy_set_header Authorization $http_authorization;
        }

        location = /v1/user {
            auth_request /auth;
            proxy_pass http://security/v1/user;
        }

        location = /v1/upload {
            auth_request /auth;
            proxy_pass http://uploader/v1/upload;
        }

        location ~ ^/v1/images/(.*)$ {
            auth_request /auth;
            proxy_pass http://minio/images/$1;
        }
    }
}
```
## Docker Compose
```YAML
version: '3.8'

services:
  nginx:
    image: nginx:latest
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf
    depends_on:
      - minio
  minio:
    image: minio/minio
    command: server /data
    ```
